# Your data

## What is collected

The collector runs in your runner. It connects as your collection role and runs a fixed, published set of `SELECT` queries. The collector asks for a read-only session. A pooler may not pass the request on. The collector runs only fixed SELECT statements either way. The collector records whether the session was read-only, and the job summary says so. It reads:

- catalog views: roles, role memberships, objects and their ACLs, default ACLs, row-level security policies, functions, which functions an extension maintains, schemas, table inheritance and partitions (parent and child table names), replication slots, publications and their tables, subscriptions and their tables, settings, the database list and its ACLs, and server times;
- configuration files, when it can read them: `postgresql.conf` and its includes, `postgresql.auto.conf`, `pg_hba.conf`, `pg_ident.conf` and `postmaster.opts`.
- facts about its own session, in its record `COLLECTION-SIDECAR.json`: the login name it used and the role it examined; whether the session was read-only (`transaction_read_only` and `default_transaction_read_only`); TLS as the server reports it for that session (on or off, the protocol, the cipher and the key bits); and the kind of client address (Unix socket, loopback, link-local, private, global or other), never the address itself. The job summary states two of them: `The collection session was read-only: yes`, `no` or `not recorded`, and `TLS to the server: yes (<protocol>, <cipher>, <bits> bits)`, `no` or `not recorded`. Behind a connection pooler they describe the pooler's session to the server.

It reads files only inside the data directory you give it (`data-dir`) and the configuration directories you name (`config-dirs`).

Three catalog views are open only to a superuser: `pg_hba_file_rules` and `pg_file_settings` on every PostgreSQL major, and `pg_ident_file_mappings` from PostgreSQL 15. `pg_read_all_settings` and `pg_read_all_stats` do not open them, so with the collection role of the quick start each one is a gap with the status `unreadable`. The readings that need it read not observed and name the view. The collector still reads `pg_hba.conf`, `pg_ident.conf` and `postgresql.conf` themselves when they are inside `data-dir` or `config-dirs`.

The collector this Action ships is generation rf32. The `postgresql-observed-baseline` check was qualified on rf28, and the collector pin its reading names is rf28 (`5fb5ca431643`); its end-to-end test feeds it rf32's own output on PostgreSQL 14, 16 and 18. rf31 reads everything rf28 reads, plus table inheritance and partitions. rf32 reads everything rf31 reads, plus which functions an extension maintains, so a SECURITY DEFINER function an extension installed is reported as the extension's, not as yours.

## What is never read

- Table contents.
- Password hashes (`pg_authid`) and whether a role has a password.
- Key material and key file contents.
- Other sessions' statements and the process list.

Secret-bearing values are withheld whole before anything is written. This covers passwords in connection strings, secret-named settings, and structured setting values such as `primary_conninfo` and `archive_command`. The subscription connection string (`subconninfo` in `pg_subscription`) is read by the collector's subscriptions query and withheld whole before anything is written. The collector then searches its own output for every value it withheld. If one is found, it deletes its output and stops, and nothing is sent.

## What leaves the runner

After the collector finishes, and before anything is checked or sent, the Action withholds free text in the runner:

- **Configuration comments.** In `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf`, `pg_ident.conf` and every file they include, the text of every comment is replaced with `# <withheld comment>`. This covers whole-line comments, comments after a setting or a rule, and commented-out settings such as `#shared_buffers = 128MB`. Every line keeps its place and its line number, and the settings and rules themselves are sent as written. A `#` inside a quoted value is part of the value, not a comment.
- **Lines PostgreSQL cannot parse.** The check must read your files as it would have read them before the comments were withheld. A line with an unclosed quote has no place where a comment could start, and PostgreSQL refuses to load a file that holds one. When the check reads such a line as a broken setting or a malformed rule, the Action replaces it with `<withheld: a line PostgreSQL cannot parse>`. That marker is not a comment: the check still counts the line as unparseable, so a broken `pg_hba.conf` still fails the reading that looks for one. When the check would read the line as a working setting or rule, no marker can carry its value without its text, so the Action stops: nothing is sent, the job exits 2 (`bad_input`), and the message names the file and the line, never the line's text. Fix the line and run again. The Action also stops, the same way, for a comment that holds a carriage return, vertical tab, form feed or Unicode line separator followed by text the check would read as a line of its own: PostgreSQL reads that text as part of the comment, the check as a separate line.
- **Lines the earlier collector withheld whole.** This applies to files collected with the earlier collector, given as `artefacts`. That collector writes `# [collect_pg: line withheld, ...]` in place of a whole line it cannot keep safely. Most such lines are comments, and they stay comments. When the line may hide a rule or a setting the check reads, the check could not read your real file, so the Action stops before sending: the job exits 3 (`collector_refused`), and the message names the file, the line or candidate lines, and the collector's reason, never the line's text. This happens for a `pg_hba.conf` rule that collector withheld whole (a quoted name, an `@file` list, a regular-expression user, an unclosed quote, a secret pattern): Assure cannot read it. Collect again with the Action. If you cannot: remove quotes a name does not need; write an `@file` list's names inline; use a `+group` role in place of a list; list a regular-expression user's roles by name. Otherwise, send Symbolia the file name and the line number through your Symbolia contact, so it is counted. It also happens whenever a file holds such a line and the collector's record of why, `COLLECTION-SIDECAR.json`, is missing, unreadable, has no record of that file, or records fewer withheld comments than the file has withheld lines: a collector output without its sidecar cannot be checked. The Action takes the sidecar from beside `raw/`, where the collector writes it. The API makes the same check before it admits a request, and a request it refuses is not charged. It also happens for a `postgresql.conf` line the server reports as the source of a setting (from `pg_settings`, or `pg_file_settings` when the collection role may read it), or that the collector's record shows as a setting line. One case remains: a `postgresql.conf` setting withheld for a control character or a secret pattern, when neither `pg_settings` nor `pg_file_settings` names its line. That covers a setting outside the collector's fixed setting list when `pg_file_settings` was not readable, and any setting, `ssl` included, on a line changed since the server last loaded the file. It carries the same record as a comment, and the check reads it as absent.
- **Lines the collector withholds.** The collector the Action ships writes a rule or setting it has to withhold as one marker line, `!collect_pg-withheld line N reason CODE`, with `setting <name>` added for a setting whose name it may show. The marker is not a comment, holds no byte of the withheld line but the setting name, and names its own line number and a reason from a fixed list. The Action keeps it as written, the check reads that rule or setting as not observed, and the summary lists it as `not observed: <file> line N (<the reason in plain words>)`. It keeps quoted names, `@file` lists and regular-expression users as written, so those rules no longer stop the check. A marker whose line number is not its own line, whose reason is not on the collector's list, that begins like a marker but is not one exactly, that follows a carriage return, vertical tab, form feed or Unicode line separator on the same line (the check would read it as a line of its own), or that sits in a JSON file, stops the upload with exit 2 (`bad_input`); the message names the file and the line. A collection that mixes this collector's output with the earlier collector's (both marker forms, or one collector's markers with the other's `COLLECTION-SIDECAR.json`) stops with exit 3 (`collector_refused`). Which collector wrote a collection is read from its sidecar. Because each marker says what it withheld, records from another run cannot hide a rule here.
- **The sidecar must belong to the files.** The sidecar counts withheld lines; it does not say which line is which. A sidecar from another run could count a withheld rule as a comment. So when a file holds a withheld line, the Action also needs the collector's `REDACTION-MANIFEST.json`, which the collector writes beside `raw/` in the same run. In your runner, before it changes any byte, the Action checks that the manifest's digest of each such file equals the file as collected, and that the manifest and the sidecar record the same withheld lines for it. If the manifest is missing, records a different digest for such a file, or disagrees with the sidecar, the Action stops: exit 3 (`collector_refused`), nothing is sent. This check has a limit. Records from another run are caught only when a file that holds a withheld line differs, byte for byte, from that run's file. Records kept from an earlier run of the same server pass if the withheld lines sit at the same places with the same marker, even where a line that was a comment is now a rule: the collector writes the same marker for both. So always use the sidecar and manifest written by the same collector run as `raw/`. The manifest stays in your runner and is never sent. This check runs in the runner, for a connection and for an `artefacts` directory, in both modes. The API cannot repeat it: the files it receives from the Action have their comments withheld, so their digests are no longer the collector's. The API checks only that the sidecar it receives accounts for every withheld line. If you call the API directly, you are responsible for sending the collector's own output from one run: `raw/` and the `COLLECTION-SIDECAR.json` the collector wrote with it.
- **Line continuation.** From PostgreSQL 16, a `pg_hba.conf` line ending in `\` continues on the next line. The declared check reads the major from `raw/declaration.json`; the intent-free check reads it from the collector's sidecar. If the two are on different sides of 16 and a `pg_hba.conf` line ends in `\`, the Action and the API stop with `bad_input`, naming the file, the line and the two sources. Nothing is guessed.
- **String literals in SQL expressions.** In row-level security policy expressions (`polqual` and `polwithcheck`), and in the `declared_predicate` of your declaration, every quoted string literal is replaced with `'<withheld literal N>'`. N numbers the different literals of one upload, so two equal literals get the same N. The rest of the expression is sent as written: column and other identifiers (quoted ones too), operators, casts, and numeric constants such as the `4821` in `pin = 4821`. An expression the Action cannot parse safely is withheld whole as one marker. No other SQL expression is collected: no view definitions, function bodies or column defaults.
- **Structured secret values** stay withheld whole by the collector, as above.

The Action does the same to an `artefacts` directory you made yourself. It works on the bytes it read, so your directory is not changed. The job log and the job summary state how many comments and literals were withheld, and how many lines were marked. They show the counts only. For a profile whose inputs name no PostgreSQL configuration or `pg_hba.conf` file, such as the HTTP profile, nothing is withheld: the files are sent as read, and the line says "nothing to withhold — the withholding pass covers PostgreSQL configuration and pg_hba files and the SQL literals in the catalog snapshot and the declaration, and this profile's inputs name none of them".

What still leaves the runner, as written:

- role names, and the names of databases, schemas, tables, views, functions, policies, publications and replication slots;
- ACLs, role memberships and role attributes;
- setting names and setting values that are not secret-bearing, such as `listen_addresses`, `port`, `ssl` and file paths;
- `pg_hba.conf` and `pg_ident.conf` rules as written: connection types, database and user names, client addresses and masks, authentication methods and options that are not secret-bearing, and identity-map names;
- policy expressions apart from their quoted string literals: identifiers and numeric constants are sent as written;
- the server version, the paths of the data and configuration directories, and the collector's record of what it read.

## What the Action sends

The Action sends the collected facts, after the withholding above, to `api.symbolia.ai` over HTTPS, with your API key, and the check runs on Symbolia's server. It sends only the files the profile reads, each within its size limit; it checks this in your runner before sending. Your database connection string and password stay in your runner. In `mode: api` the Action also sends, by default, the text of the `requirements.md` at your repository root (when it is there and within 65536 bytes, 256 lines and 8192 bytes per line), your repository name and the commit (on a pull request, its head commit); the server keeps them with the check for 30 days. Set the `requirements` input to `none` to send no requirements text. Setting `requirements` to `none` stops the requirements text only: the repository and the commit are still sent and kept with the check for 30 days. The Action reads the requirements text from the files your workflow checked out; the commit it sends is a label for the run, not the source of the text. On `pull_request` the checkout is the merge commit GitHub made, and on `pull_request_target` it is the base branch, while the commit sent is the pull request's head commit.

The Action writes the verdict file, the job summary and the annotations in your runner. The job summary stays in your workflow run, under your own GitHub retention settings. The verdict file stays on the runner unless you upload it as a workflow artifact. The summary and the annotations show the reason for each reading, and for each `fails` reading its witness. Both can hold role, object and path names from your system, bounded and escaped. They appear in your own CI log, which anyone can read for a public repository. On the summary lines and in the annotations, each invisible format character in a requirement's sentence (such as a zero-width joiner or non-joiner, or a direction mark) is shown as one space, so a word joined by one can read with a space inside it; the verdict file and the API keep the sentence exact.

The `assure` agent skill (`skills/assure/` in the Action repository) is documentation only: it sends nothing itself.

The scratch folder is removed when the check ends. If the server is stopped during a check, a daily cleanup job removes any scratch folder older than 30 minutes. When the server starts again, that check reads `checker_error` with the reason "the server restarted while this check was running; submit it again", and it is not charged.

A check is charged once the checker starts, whatever its result. A request refused before the checker starts is not charged, but it counts against your rate limits; a request refused for its rate or credit is refused from its headers alone, before its body is read or parsed. A result is returned whenever one can be produced: a machine whose checker output is malformed, or whose readings the server could not write, is refused and named with its reason, and the other machines keep their readings. When no result can be produced, the typed failure says what was malformed (`detail.malformation`: a kind from a fixed list, the file, the line, the field and the expected form), never the text of your input.

The verdict holds the readings, which include facts observed from your files, such as role names and settings. It also holds each file's name, size and sha256, and the time its check completed. It holds no file contents.

The request log holds ids, sizes, outcomes and timings only: time, request id, key id, account, method, route, status, outcome, bytes in and out, file count, check id and duration. When a charge cannot be recorded, one more line says so (`event: charge`, `outcome: charge_failed`), with the account, check id, byte count and the check's outcome. When the server could not write one machine's readings and returned the others, one more line says so (`event: server_fault`), with the account, check id and the machine names. The log never holds a request body, a file name, file contents, a key or a header value.

Each check runs in its own process, separate from the server process. Two things keep that process off the network:

- The serving code it runs imports no network client and no model client. A test enforces this: it reads every source file of the serving code and the Action and fails if one imports a network or model client module. There are two exceptions: the Action's own client of the API, which runs in your runner, and the report writer, which only the separate report service imports (below).
- The server's systemd service configuration denies the service, the check process included, every outbound network address except the machine's own loopback.

### The report

When a report is requested (the Action does so by default in `mode: api`, and `report: false` keeps the verdict record from being sent to OpenRouter; or `POST /v1/checks/{id}/report`), a separate service on the server, the report service, sends one request to a language model: the writer's fixed instructions and the verdict's record. The record is each rule's status, reason and evidence, the first line, the policy and the engine's release digest. Like the verdict, it holds facts observed from your files, such as role names and settings. Nothing else is sent: never your files or their names, sizes or digests, and never your account, key or check id.

The request goes over HTTPS to OpenRouter, which passes it to the model's provider, for the model `openai/gpt-6.1-sol`. The report service may reach only OpenRouter's addresses; the API service and the check process still reach no outside address. Each attempt is one writer call. That call is sent again once, only after a server error or a timeout, and a failure of any other kind withholds the report without a second request. Neither the request nor the model's raw answer is stored. A deterministic check reads the written text against the record, and a text that fails a fact rule is withheld and not kept. A text that passes every fact rule is served as written, even when it misses a style target (reading grade, sentence shape or one of the writing rules for plain words); the report's `lint` records any style miss.

The report record is stored beside the verdict and deleted with it. One ledger row records the report's tokens, cost, route, model and attempt. A report is charged on its usage line: free within your plan's monthly allowance (on Premium and Pro, one pool shared with formalisation and proof search: USD 20 or USD 200 of usage a month, at the same rate as overage (cost x 1.2)), and at cost x 1.2 for the part beyond it, up to the overage budget you set; overage is off until you set a budget. The free plan has a report balance of USD 1, granted once per verified email; it does not renew. A top-up of your account never extends the free report balance. A free report is paid from the balance at its real cost; if that cost passes the quote the balance can go below zero, further reports stop, and a recharge first clears what is owed. A recharge first clears what is owed; the rest is credited to your account's top-up, and the free report balance itself is never extended. A free report whose quote is beyond what is left of the balance is refused before anything runs. A free report is never charged, whatever `allow_overage` says. One job's quote can be at most USD 50 unless you ask Symbolia to raise your account's job ceiling; the quote comes first. While Assure is in beta a withheld report is not charged. Its model call is still recorded in the ledger at its cost. The server records each attempt in the usage ledger before it calls the model, and reads the attempt count and the wait between attempts back from the ledger on every pass, so a restart resets neither; when that record cannot be written, the model is not called. The server starts at most three attempts for one report, even when two report services share the ledger, and three attempts can mean up to six requests to OpenRouter, because each attempt sends its request once more after a server error or a timeout.

Symbolia's own qualification accounts may keep the writer's raw text beside the report record, on the server, to qualify the writer. That setting exists only for Symbolia's own accounts and is never set for a customer: the code refuses it for any account on a customer plan, and the API never serves that text. A withheld report's record keeps the names of the deterministic check's rules and a count for each, never sentences of the refused text. One telemetry line records the hour, the profile, whether the report was written or withheld, the route, the model as the gateway named it, the attempt, the token counts, the cost, whether the deterministic check passed and the names of the rules it failed, and why a report was withheld. It holds no text of the report, no names or values from your system, and no account, key or check id. Every value in it comes from a fixed list kept in Assure's code, or is a number. It is kept for 12 months, then deleted.

### Deliberate feedback

The Action sends no feedback by default. Its `feedback` input accepts one deliberate JSON string or a workflow-written JSON file path. Only `mode: api` sends it, once after a check with a server check id; the Action attaches that id and never retries. Local and lint runs send none. A feedback error adds a typed outcome to the summary without changing the verdict file, outputs or exit. Customer text is data, never instructions; it is not echoed into commands or the summary. Include only text the customer permits you to send, without secrets or collected configuration.

Feedback goes to Symbolia's API and is never sent to a model or consulted by the checker or report writer. It is free, with no charge or usage ledger row. `report: false` stops the check record going to OpenRouter; it does not disable deliberate feedback. Text is limited to 4,096 UTF-8 bytes and the body to 16,384 bytes. Up to 100 new notes per account per UTC day are accepted, sharing the checks' minute rate window. Same-account notes with the same kind, check id and exact text on the same UTC day return the original row rather than storing another. Follow-up consent defaults to false.

The authenticated `GET /v1/feedback/{id}` returns only that account's note, including its exact text and `rows_unreadable`, the number of unreadable lines in its day file. Other accounts' ids, absent ids and malformed ids receive the same `not_found`. The daily digest reads notes without writing: kind and package counts with distinct account counts, bounded text from every kind for triage regardless of consent, consenting notes and friction check ids. Consent controls follow-up only; it does not hide a submitted note from triage. Account ids are displayed as stable short hashes. Customer text is displayed only as bounded, cleaned `DATA>` lines in fenced data blocks; it is never instructions. Skipped or unreadable files and unreadable rows are counted, including zero. When the feedback collection cannot be accessed, the digest stops with an error instead of reporting an empty day. The digest makes no model call and creates no automatic demand-ledger entry or model proposal.

### Checker telemetry

For each check that reached the checker, the server keeps one short record to improve the checks: what the checker could not read or judge, and which versions it met. It holds the hour of the check (not the minute), the profile and its version, the engine and checker versions, the PostgreSQL major version only (such as 17), the collector's version, the outcome and the policy reason, the number of readings in each status, for each of Assure's own obligation ids the number of its readings in each status, which machines were read and, for each machine that could not be read, a reason chosen from a fixed list (such as "file absent"), which of the collector's own queries could not be read with a fixed error class (such as "permission denied"), which of the expected input files were present, the number of comments and string literals withheld, the size of the upload as a range (the next power of two, such as "at most 4,096 bytes"), the number of files as a range (such as "2 to 4"), and the time the check took, in a range. It holds no names or values from your system: no role, database, schema, table, function, policy or setting name or value, no address, no file path, no reason text and no file contents. It holds no account, key or check id. It is not designed to be joined to your account, but that cannot be ruled out: in an hour with few checks, the hour alone could associate a record with one check in the charges ledger, which holds each charged check's time, account and check id, or in the request log (kept 90 days), which holds each request's time, account, check id, exact file count and body size, and is the only record of a check that was not charged, such as the checker's own internal error; and while a verdict is kept (30 days), a record's statuses and which input files were present could match that verdict. Every value in it comes from a fixed list kept in Assure's code, or is a number. It is kept for 12 months, then deleted. The Action sends nothing extra for it.

## Paid formalisation

Symbolia opens paid formalisation for an account by name. Until it is open for yours, the quote stays free and nothing is sent to a model. The rest of this section describes a paid run once it is open.

A requirement no method states carries a free quote (the API quick start, "The free formalisation quote"). The quote comes first and calls no model. Nothing is sent to a model before you ask for a paid run and accept its quote. A paid run starts only when its quote is within your remaining allowance plus the overage budget you have enabled; otherwise it reads `budget`, uncharged. This section says what that run sends where.

**What leaves your runner.** The repository bundle the paid run reads: the files under `raw/repository/` with `raw/REPOSITORY.json` (each file's path, size, SHA-256 and mode, with the commit and tree ids), your declaration in `raw/declaration.json`, and the `requirements.md` text. Python files are parsed on the server. Files that are not Python are counted and digested, never parsed. The bundle goes to `api.symbolia.ai` over HTTPS with your API key, as every check does.

**What the server sends to a model.** The proposal request carries the candidate model the server extracted from your source, with the requirements text. The candidate model is the server's reading of your routes and guards: the route ids, the module and line of each route and guard, the view and guard names, and the session keys, with the decorators each route lists and the session writes each view makes. It is more than one sentence: from the whole candidate, the model proposes a formula for every eligible requirement sentence. A second request reviews each proposed formula. The review request carries the sentence, the plain-language reading of the proposed formula and the meaning of each declared name, and no byte of your source.

**The model and the route.** The request goes over HTTPS to OpenRouter for the model `anthropic/claude-opus-5.5`. After a typed failure on that route, the request goes once more to Anthropic's enterprise route for `claude-opus-5-5`. No third route is taken: when both fail, the sentence reads `route_exhausted` and no other model is called. Every result records the route taken, the model id the route returned and the tokens used.

**The Lean check.** The Lean check runs on Symbolia's own host, as CPU work with no model call. It checks each proposed formula that reads holds against the finite machine extracted from your source. Its CPU time is measured, and is quoted and charged at zero until a CPU rate is published; the charge never exceeds the quote.

**What is kept, and for how long.** The files you send go to a scratch folder made for this one run and are deleted when the run ends, whatever the result. The verdict is kept 30 days, then deleted. Your requirements text and its SHA-256, the repository and commit, and the id, schema and SHA-256 of your declaration are kept beside the verdict for 30 days, then deleted. The quote and the charge, with each stage's tokens, cost, route and model, are kept with the charges. A formula the run establishes is kept for your account as a stored method, so the same sentence is never quoted again: it holds the formula, the digests of the records that produced it and the route taken, never your source bytes, a verdict, a reading or a requirement line number.

## Tenant separation

- Each check gets its own scratch folder, created for that check alone and removed when it ends.
- Verdicts are stored per account. Check ids are random 128-bit values.
- Every read checks the account. Another account's check id reads `not_found`, the same as an id that does not exist.
- Idempotency keys are per account. The same key from two accounts names two separate checks.
- Nothing is cached across accounts.
